A candidate above the recommended error threshold remains inspectable and may be committed only through one explicit `Bake Anyway` warning with no remembered bypass; preview identifies affected tracks/lanes, maximum error and time, and offers interval adjustment or Adaptive recomputation. Non-finite data, invalid boundaries, outside-trajectory failure, stale state, and resource limits remain hard blockers, while Adaptive target misses also remain uncommittable.
- **Trajectory fidelity profile**: Bake and Remove Redundant Keyframes share High Precision (`0.1%`, `0.001` block, `0.01°`), Balanced (`0.5%`, `0.005` block, `0.05°`), Draft (`2%`, `0.02` block, `0.25°`), and Custom presets but select them independently per operation; Bake defaults to Balanced and removal defaults to High Precision. Position, translation, relative, zoom, and raycast use block caps; rotation and FOV use degree caps. Every affected Additive Lane and accumulated Scalar Animation Track must satisfy the relative and actual-unit limits, with excursion-aware scale and unit-only handling for near-flat ranges. Bake retains its Adaptive and Fixed rules; LINEAR-only removal computes exact error at the union of affected source-key times without validation probes, protects candidates that exceed tolerance, permits no force override, and previews removal/protection counts plus maximum error and time.
- **Bake validation probes**: Maximum Validation Probe Gap is temporary validation density, never an output-node cadence: High Precision `0.025s`, Balanced `0.05s`, Draft `0.1s`, or a finite positive server-bounded Custom value. It uses logical seconds and 20 TPS, not Display Frame Rate. Scope endpoints, source keys, discontinuities, and known extrema are mandatory probes; Adaptive promotes only deterministic failing probes into nodes, while Fixed uses probes only for error measurement. Probe and generated-key budgets are separate, and incomplete validation is a hard blocker in both modes.
- **Bake simplification boundary**: Bake is Non-Simplifying: it commits exactly the retained and generated keyframe set shown in its preview. It never removes retained source keys, Boundary Anchors, discontinuity keys, promoted adaptive probes, or Fixed Interval grid samples through a hidden post-pass, and exposes no initial `Optimize Result` checkbox. Redundant-key removal is a separate previewed project operation, revision, and Undo/Redo item; undoing it restores the post-Bake set before a later Bake undo restores the pre-Bake content.
- **Redundant-key candidate scope**: Remove Redundant Keyframes defaults to eligible Selected Keyframes, never intersects that selection with Work Range, and may use unselected neighbors only as read-only validation context. Its explicit Tracks in Time Range mode separately chooses Selected Tracks or All Populated Numeric Tracks and Work Range, Full Animation, or a preview-local Custom Range; only in-range numeric nodes are candidates, Track Groups expand populated numeric children, Additive Lanes remain independent, and command events, markers, empty tracks, and visibility filters are excluded. Missing implicit scope never falls back to the whole animation, and every scope or baseline change rebuilds or invalidates the preview before server identity revalidation.
- **Redundant-key curve reconstruction**: Remove Redundant Keyframes is optional and may process eligible manually authored or post-Bake content, but it is never an automatic or required Bake stage. Its initial release only deletes interior nodes from continuous `LINEAR` runs within one Additive Lane, reconnects surviving neighbors with `LINEAR`, and accepts deletion only after full affected-interval trajectory validation; Lane endpoints, `CONSTANT` discontinuities, and any Easing- or Bézier-adjacent nodes and segments are protected rather than fitted or rewritten.
- **Redundant-key reduction order**: Each non-candidate or protected node is a fixed anchor. The optimizer repeatedly simulates every currently eligible deletion, scores the complete provisional result by its worst normalized relative or actual-unit fidelity consumption across affected Lanes and accumulated Tracks, and accepts the lowest passing score. Every score remains relative to the immutable operation-start trajectory; affected neighbors are rescored after each provisional deletion. Equal scores resolve by canonical Track order, Lane order, Timeline Time, then stable node identity. The process stops when none pass, validates the complete result again, and promises deterministic bounded-quality output rather than a globally minimum key count.
- **Redundant-key execution model**: Preview and confirmation use Bounded Key-Reduction Runs rather than the render or server thread. Client preview is latest-wins per Project Tab on a finite editor worker; server confirmation authoritatively recomputes from a bounded immutable numeric snapshot and is single-flight per player/project with no duplicate queue. Candidate count, evaluations, snapshot bytes, queue wait, and compute time are all finite. Scope/settings edits, tool or tab exit, lifecycle exit, relevant accepted edits, cancellation, timeout, or exhaustion release task state and yield no partial result, precision relaxation, scope truncation, or automatic retry. Progress is phase-based and throttled; only a complete current result may reach the server-thread terminal gate and atomically create one revision and Undo/Redo item.
- **Redundant-key resource budget**: Built-in hard maxima per run are `20,000` deletion candidates, `100,000` source scalar keys, `512` affected Additive Lanes, `20,000,000` exact scalar error comparisons, and a `16 MiB` immutable snapshot. Client preview has a `10s` deadline, one active calculation and one replaceable latest pending request; server queue wait is `5s`, active computation is `15s`, global execution permits two active and four queued tasks, and all retained server reduction snapshots together are capped at `64 MiB`. Progress is capped at four updates per second. Servers may lower but not raise these limits and advertise the effective policy to clients; integrated servers use the same policy. Whichever per-task, queue, or aggregate-memory limit is reached first rejects the complete operation with actual-versus-limit diagnostics and no partial result.
- **Redundant-key range boundary**: Tracks in Time Range treats its closed Time Scope as a strict structural cut. A candidate is Boundary Protected whenever deleting it would create a replacement `LINEAR` segment that crosses either range endpoint, including a node exactly on an endpoint with an outside neighbor; protection applies even when the replacement is mathematically collinear or zero-error. No Boundary Anchor is inserted, and every out-of-range node, identity, value, time, interpolation adjacency, and segment remains unchanged. Fidelity tolerance applies only inside the range. Preview reports Boundary Protected candidates and suggests widening the range, using Full Animation, or explicitly choosing Selected Keyframes; Selected Keyframes has no implied temporal boundary and instead validates its complete affected interval.
- **Pristine empty track**: Remove Empty Tracks may delete only an instantiated Scalar Animation Track whose Additive Lanes contain zero accepted keyframes and whose stored structure is either Lane-free or exactly one untouched system-created default empty Lane. Any named or reordered Lane, multiple-Lane layout, Legacy Group Lane including an imported lane named `default`, import/export metadata, or other durable authored reference protects the track. Empty Lanes inside a nonempty track are outside this tool. UI visibility, collapse, color, filters, and selection are not authored content, while an active draft, gesture, lock, or valid operation reference temporarily protects the candidate. Removal changes neither trajectory nor duration, does not delete Track Groups or supported channel definitions, and later authoring rematerializes the track and default Lane. Preview lists removable and protected structures; authoritative commit is one atomic revision and Undo/Redo item.
- **Empty-track cleanup scope**: Remove Empty Tracks exposes Selected Tracks, Current Animation, and Whole Project as mutually exclusive explicit scopes. Any selected instantiated Scalar Animation Track or Track Group defaults to Selected Tracks, with groups expanding their instantiated scalar descendants; without such a selection the tool opens unresolved and never falls back to Current Animation. Current Animation and Whole Project require deliberate selection, Whole Project is never a default, and no scope intersects another. Work Range, Custom Range, channel visibility, filters, virtualization, and viewport presence are irrelevant. Preview groups Whole Project findings by animation and lists removable and protected tracks; zero removable candidates disables confirmation and creates no history. Any relevant baseline or eligibility change invalidates the whole preview, and one accepted cleanup is one atomic project revision and Undo/Redo item.
- **Empty-track scan execution**: Client preview and server confirmation use independent Bounded Empty-Track Scans on the shared finite camera-editor work facility. Each Project Tab keeps one active latest-wins preview; confirmation reconstructs candidates from the authoritative baseline and never trusts client identities alone. The immutable summary contains only animation/track/Lane identities, key counts, Lane type/name/order flags, import/round-trip metadata, and activity/reference protection flags, never keyframe values, curves, full documents, players, worlds, or UI objects. Built-in maxima are `100,000` instantiated scalar tracks, `250,000` Additive Lanes, and `8 MiB` per summary; client preview, server queue wait, and server scan each have `5s` deadlines, with at most four progress updates per second. Effective project/collaboration limits apply first, administrators may only lower advertised scan limits, and integrated servers enforce the same policy. Scope or lifecycle changes, cancellation, stale baselines, timeout, or exhaustion release state and produce no partial list, automatic narrowing, or retry. Phases are structure collection, empty-track classification, protection validation, and summary generation; atomic commit has one terminal outcome.
- **Empty-track cleanup reconciliation**: A successful Remove Empty Tracks commit broadcasts the structural update to every open tab for that project and removes deleted track identities from local selection, focus, and Inspector state without deleting channel support. Surviving Track Group selection remains; no neighboring row is auto-selected. Focus moves to the nearest surviving focusable row or the track-tree container, and the Inspector falls back to Current Edited Animation or empty selection. Current animation, playhead, play/pause state, Work Range, timeline zoom, and horizontal scroll remain unchanged; vertical virtualization uses a stable surviving-row anchor, and Whole Project cleanup never switches or opens animations. Undo restores exact track and Lane identities, order, and stored structure but does not revive stale local selection or focus, and reports the restored count through the status surface.
- **Timeline hierarchy**: Use four same-level groups: Position (`X/Y/Z`, `TRANSLATION_X/Y/Z`, `RELATIVE_X/Y/Z`), Rotation (`ROTATION_X/Y/Z`), Camera Parameters (`FOV`, `ZOOM`, `RAYCAST`), and Animation Effects (command events only). Do not add a “basic position” intermediary group and do not make camera parameters children of Position or Rotation.
- **Timeline interaction**: Keep the timeline body clean without hover/selection control strips. `Ctrl` plus left click adds or toggles multi-selection; `Shift` plus left click removes. Same-type node overwrite asks for confirmation, revalidates targets, and treats movement plus overwrite as one atomic operation. F3 toggles the graph editor; XYZ curves use RGB-like colors and unselected curves are dimmed. Numeric keypad left/right switches fields.
- **Events and Bézier**: Particle and sound events were removed from the initial design. Command effects execute once from the camera-playing player with suppressed command feedback; recipient selectors must begin with `@p` and may include parameters. Command-event editing uses a personal lock and read-only state for other editors. Bézier nodes keep the ordinary diamond appearance; two touching Bézier nodes present as linear, while three or more touching nodes render a normal Bézier curve. Easing-to-Bézier conversion must preserve the original trajectory closely and produce editable curves; Bézier-specific implementation details may be decided by the AI unless a later user decision overrides them.
- **Properties and overlays**: Animation properties open from Properties or double-click and select existing names on open. The shared Editor Overlay Layer is defined by ADR-0203: Tooltip Layer, Anchored Utility Surface, Property Modal Surface, and Blocking Transaction Surface. Tooltips for buttons wait more than one second, do not reflow or take focus, and all overlay surfaces restore focus without changing playback or project state. Only one blocking surface may own input.
- **Status feedback**: ADR-0204 adopts dual feedback: the bottom status bar is the persistent source of truth, while one short-lived, non-blocking Transient Status Notice may appear near it for meaningful operation results. Notices are bounded, coalesced, session-scoped, clickable to read-only status details, and never replace field validation or blocking confirmation.
- **Documentation boundary**: When camera framework or camera UI code is eventually modified, inspect the exact changed behavior and update or create the corresponding Markdown article under `.wikidoc` in the same task. Prefer MixinExtras APIs for new/refactored Mixins only after verifying the local dependency and API; do not mechanically replace correct native Mixins.
