# Structure the camera editor overlay layer

The Reconnect Draft Review Surface defined by ADR-0207 is a Blocking Transaction Surface and therefore follows the single-blocking-surface, responsive scrolling, focus, and lifecycle rules in this ADR.

The Camera Animation Editor uses one responsive Editor Overlay Layer above the Workspace Shell. Every ephemeral surface belongs to an explicit layer and follows one input, focus, dismissal, placement, and lifecycle contract rather than implementing independent ad-hoc popups. The visual language remains the established Blockbench-inspired dark theme with blue selection and restrained scrims; the overlay system changes layering and behavior, not the underlying project semantics.

The overlay order is:

1. `Tooltip Layer` for delayed, passive explanations beside qualifying buttons. It never receives keyboard focus, captures input, changes layout, or survives a target or containing-surface change.
2. `Anchored Utility Surface` for top menus, context menus, command completion, and compact selectors. It is positioned relative to its trigger, flips or clamps when space is insufficient, closes on outside-click or `Esc`, and does not mutate project content merely by opening or browsing it.
3. `Property Modal Surface` for Animation Properties, marker properties, and command-event properties. It uses a responsive dark title bar, grouped fields, scrolling content, and fixed bottom actions. Outside-click does not dismiss it; `Esc` cancels the complete local draft transaction; `Enter` confirms only when the focused control permits it; name inputs select their existing text on open. A locked command event uses the same surface in read-only mode and never bypasses its personal lock.
4. `Blocking Transaction Surface` for overwrite confirmation, project migration, checkpoint restoration, deletion, replacement import, and other high-impact or progress-bearing operations. It uses a restrained input-blocking scrim, defaults focus to the safe cancellation action, revalidates permission, authority, revision, locks, target identities, and resource state at the relevant boundary, and exposes truthful loading, success, failure, cancellation, retry, and refresh states.

Only one Blocking Transaction Surface may own input at a time. A higher-priority surface dismisses irrelevant lower-priority tooltips and utility menus; nested steps are represented as state changes inside the active blocking surface or as an explicitly serialized transition, never as an unbounded stack or hidden queue of dialogs. A Property Modal Surface may remain open while ordinary field validation appears beside its field, but it cannot be silently replaced by a second property editor. Non-modal status notifications, including the Transient Status Notice defined by ADR-0204, and ordinary docked panels are not blocking overlays and retain their own lifecycle contracts.

All overlay surfaces use relative, responsive placement rather than fixed Minecraft screen coordinates. They prefer the trigger-adjacent placement, automatically flip when needed, clamp to the available bounds, keep critical actions reachable, and turn content into a scrollable region instead of shrinking the whole editor. The underlying viewport, timeline, playhead, selection, playback state, project tab, runtime camera, and collaboration session do not change merely because an overlay opens, closes, or is browsed. Opening stores the invoking focus target; closing or reaching a terminal result restores focus to that control or to the nearest still-valid target under Overlay Focus Restoration.

Validation errors remain local to the relevant field whenever possible. Blocking operations must provide real progress and terminal outcomes rather than an indefinite spinner; failure preserves the pre-operation state and offers only the recovery actions valid for that state. Every button rendered by an overlay is operational, inherits the delayed tooltip contract where applicable, and exposes an accessible enabled, disabled, or read-only reason. These rules are presentation and interaction constraints layered over the existing transaction, collaboration, lock, checkpoint, migration, and Undo/Redo ADRs; they do not create hidden project revisions or convert UI state into persisted animation data.
