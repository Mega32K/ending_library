# Do not block lifecycle commit on camera restoration acknowledgement

A successful Project Runtime Lifecycle Drain removes every affected Project Runtime Instance and invalidates the Active Runtime Revision on the server without waiting for client acknowledgement. After that commit point, each online target receives an idempotent `Camera Restoration Delivery` correlated with the terminated runtime instance and lifecycle operation. The client applies its Camera Restoration Snapshot when still valid or the safest verified player-camera fallback otherwise, then may acknowledge completion. Missing, delayed, duplicated, or malicious acknowledgements never roll back archive or deletion, recreate an instance, or keep the project lifecycle transaction open.

Delivery retries and diagnostics are finite: the server keeps only bounded immutable correlation data, retries at a controlled cadence until a configured deadline or acknowledgement, releases the delivery record at every terminal outcome, and never retains player, world, camera, or project-document objects through the retry state. A player disconnecting during delivery is handled by the existing idempotent disconnect cleanup and ends that delivery attempt. Timeout records one bounded diagnostic outcome and releases all retry state. A late or duplicate restoration instruction is harmless because the client rejects stale runtime identities and restoration remains idempotent.
