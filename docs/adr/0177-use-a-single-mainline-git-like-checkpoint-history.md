# Use a single-mainline Git-like checkpoint history

Every accepted atomic project edit creates one immutable, lightweight Revision Commit Node containing its parent authoritative revision, operation metadata, affected scope, and content fingerprints. The node does not duplicate the complete project document in the history record. A Named Project Checkpoint is the user-facing “检查点” and an internal label similar to a Git tag; it points to one immutable Revision Commit Node and carries its own stable identity, name, description, creator, creation time, and retention state. The checkpoint target is selected at creation and cannot be changed; a different target requires a new checkpoint. The checkpoint panel and project history panel may show the checkpoint, its target node, the parent relationship, and comparisons without opening a second editable working copy.

The project has one authoritative editing mainline. Accepted collaborative operations continue that mainline regardless of whether a checkpoint is created. The initial implementation deliberately excludes independent branches, branch switching, merge, cherry-pick, and branch-specific permissions. This preserves the existing Owner/Editor collaboration model and avoids introducing a second conflict model on top of field-level collaboration conflicts.

Restoring a checkpoint does not move the mainline head backward and does not delete later history. After the normal permission check, Checkpoint Restore Preflight, difference summary, and destructive lock-drain rules succeed, the server creates the required Protection Checkpoint and applies the selected label's target content as one new authoritative full-document revision whose parent is the current mainline head. The restore operation therefore creates a new Revision Commit Node visible in the operation journal and history, and later edits continue from the new head.

Checkpoint creation, metadata editing, pinning, comparison, and inspection remain separate from content editing. Owners and Editors may change the user-facing name or description without changing the immutable target; creating, renaming, or deleting a checkpoint does not enter personal Undo/Redo, while restoring one remains the existing special undoable Restore Checkpoint Operation. Stable node, label, and snapshot references are retained only under the finite project retention policy; an expired content reference leaves its metadata inspectable as `Unavailable` and never creates an approximate replacement.

More than one checkpoint may point to the same Revision Commit Node. These checkpoints share the target's durable reconstruction anchor but retain independent metadata and pin state. Checkpoint names remain unique within the project, so every user-facing restore, compare, or management action identifies one checkpoint without relying on an internal UUID display.
