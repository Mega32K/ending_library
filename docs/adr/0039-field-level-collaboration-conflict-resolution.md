# Merge disjoint fields and reject overlapping collaboration edits

The collaborative editor uses optimistic, non-locking editing with semantic conflict checks rather than last-writer-wins replacement. Every content operation declares an Operation Footprint composed of stable logical object and field paths: for example, a keyframe identity plus its timestamp, value, or curve data; a track or lane identity plus its metadata; or a structural parent affected by creation, deletion, rename, or reordering.

This general non-locking rule has one scoped exception in the initial camera editor: command-event editing follows the Command Event Personal Edit Lock defined by ADR-0144 and its complete-event scope in ADR-0145. The exception applies only while one participant is actively editing one command event and does not turn the project, other tracks, or unrelated events into locked content. Any non-holder operation whose footprint changes the locked event's command text, authored time, same-time order, existence, identity, or relevant structure is rejected as locked before ordinary stale-revision merging; operations that do not modify the locked event continue under the normal footprint rules.

When an operation's expected revision is current, the server validates and applies it normally. When it is stale, the server compares its footprint with the footprints of accepted operations since that revision. Different tracks, different Additive Lanes, different keyframe identities, and different fields of the same keyframe may be merged when the resulting state remains valid. A client is not asked to download and silently replay against a new baseline; the server performs the semantic rebase explicitly and reports the resulting authoritative revision.

The server rejects the complete transaction when it touches the same field, the same curve segment, the same keyframe identity in an incompatible way, or a structural ancestor/descendant whose ordering or existence could change the meaning of another operation. Creation, deletion, rename, lane movement, track movement, and other structural edits use conservative structural footprints; they are not treated as independent merely because their serialized JSON locations differ. Delete-versus-modify is a structural conflict. No conflicting transaction is partially applied or converted into last-writer-wins data.

Conflict responses identify the affected logical objects and the current authoritative revision, provide enough current values for the UI to explain the conflict, and leave the rejected client's local preview uncommitted. The same footprint comparison governs normal edits, Auto Key transactions, curve edits, imports that become content operations, personal Undo/Redo compensations, and checkpoint restoration. A checkpoint restore and its compensations use a full-document Restore Footprint and therefore conservatively conflict with concurrent or later content changes rather than behaving as last-writer-wins replacements.
