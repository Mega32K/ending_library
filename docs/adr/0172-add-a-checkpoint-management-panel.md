# Add a permission-aware checkpoint management panel

The File menu opens a responsive, dockable Checkpoint Management Panel for the active editable project. The panel lists each user-facing Named Project Checkpoint with its name, optional description, creator, creation time, immutable target Revision Commit Node, pin state, reference state, and retention state. Internally each checkpoint is a Git-like label, but the UI does not present it as a generic classification tag. It can inspect accepted checkpoint content without including local drafts, editor workspace state, runtime instances, or unpublished transient preview state. The panel presents the single-mainline parent relationship as read-only context and does not expose branch, merge, cherry-pick, or retarget actions.

When multiple checkpoints point to the same revision, the panel groups them under the common revision without merging their metadata or lifecycle controls. Search and filtering can still return each checkpoint independently. Names are unique within the project under trimmed case-insensitive comparison. System Recovery Points are not mixed into this ordinary checkpoint list; they remain in the History and Recovery surface.

Project Owners and Project Editors may open the panel, create checkpoints, and edit checkpoint names or descriptions. A metadata edit is server-ordered against the current metadata version; the first accepted concurrent edit wins, while a stale edit is rejected and refreshed instead of silently overwriting another participant. Only the Project Owner may pin or unpin checkpoints, restore a checkpoint, or request checkpoint deletion. Editor-facing disabled controls remain explanatory under the shared Button Tooltip contract and identify the owner-only restriction or another current blocking condition. A read-only project tab may inspect trusted checkpoint metadata only and cannot create, rename, restore, pin, unpin, or delete checkpoints.

Restore starts with Checkpoint Restore Preflight and a bounded Checkpoint Difference Summary. The summary is summary-first: it shows project-level counts, then expandable animation- and track-grouped Checkpoint Difference Detail for authored values, keyframes, curve segments, command events, markers, and animation properties. Large sets use a virtualized scroll region, and an optional raw-data view remains secondary and read-only. The panel may open a Checkpoint Target Preview that does not mutate or synchronize the active project. The server revalidates permission, stable checkpoint identity, current accepted baseline, references, retention availability, and affected command-event locks before draining leases or mutating the project. A failed preflight leaves the panel, selection, drafts, locks, and project state unchanged. A successful restore follows ADR-0040: it becomes a new full-document project revision, is visible to collaborators, and enters the initiating owner's personal history without silently rewinding the durable journal.

Deletion and retention display reference-aware behavior. A pinned or referenced checkpoint is not physically removed immediately; the panel shows Pending Cleanup and identifies the blocking reference categories. A checkpoint that becomes unavailable to a surviving history action is marked Unavailable rather than replaced by an approximate version. All panel actions preserve playhead, playback, current selection, workspace layout, and local drafts unless the restore's established destructive preflight explicitly requires their handling.
