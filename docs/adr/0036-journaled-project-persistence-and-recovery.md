# Persist collaborative edits with an operation journal and atomic snapshots

The server-owned in-memory Project Document remains the authoritative editing state. After validating and ordering an Edit Operation, the server applies it to that document, assigns the next Authoritative Revision, creates one lightweight Revision Commit Node containing the operation metadata and content fingerprints, and appends the accepted operation to that project's ordered Operation Journal. A client operation remains pending until the server acknowledges its accepted revision and persistence status; rejected or unacknowledged operations never masquerade as durable project content.

The server periodically writes a Project Snapshot after a bounded interval or operation count, and forces a Durable Checkpoint for Project Save, Named Project Checkpoint creation, project close, applicable world save, and normal server shutdown. Snapshot creation writes a complete versioned document to a temporary file and atomically replaces the active document only after successful serialization and validation, retaining the previous valid recovery copy. A completed snapshot records the highest included revision, after which journal entries at or before that revision may be compacted.

Crash Recovery loads the newest valid project snapshot, falls back to its recovery copy when necessary, and then replays strictly later journal entries in revision order. Invalid entries, revision gaps, or replay failures stop automatic replay and place the project into a visible recovery-required state; the loader never silently skips an accepted operation and continues with an unverifiable result. Failed snapshot creation leaves the preceding snapshot and uncompacted journal available.

Project opening performs Project Format Version inspection before an editable Editing Session begins. A supported older document is migrated only through a deterministic all-or-nothing server operation: the server first retains an exact Migration Protection Checkpoint, validates the complete converted document, and atomically replaces the active project file only after every step succeeds. A failed migration leaves the original file and recovery material untouched, creates no partial journal result, and does not open an editable session. A document newer than the supported Project Format enters a Newer-Format Read-Only State and is never rewritten or silently downgraded.

Project Save and Named Project Checkpoint creation are separate user-facing operations. Project Save is the Lock-Neutral File > Save or `Ctrl+S` action: it flushes accepted edits and requests an atomic snapshot but does not create a named retention entry. Named Project Checkpoint creation first performs the same accepted-content flush, then stores a separately identifiable label pointing to the selected accepted Revision Commit Node, with its confirmed name and optional description. Neither action confirms local content drafts. Active property previews, Auto Key proposals, Command Event Creation Drafts, and other local content drafts remain private and retain the Project Tab Draft Dot; active command-event drafts are neither included nor discarded, and their leases remain active. Checkpoint retention is deliberately generous but finite: pinned labels and snapshots referenced by eligible Undo/Redo, restore protection, or active collaborative preview are protected from deletion, while the oldest unpinned and unreferenced versions are eligible for cleanup. Project Workspace Snapshots remain session-scoped UI state and are never written into the durable animation journal.

Checkpoint restoration is a durable, server-authorized transaction rather than a file replacement. If affected command-event leases exist, the owner must complete a Destructive Project Preflight before the Destructive Project Lock Drain and restore can commit. Before applying the selected checkpoint, the server creates and durably names a Protection Checkpoint for the current authoritative state, validates both snapshot references, and records the restore metadata in the Operation Journal. The target content then becomes a new authoritative revision. The restore record and both referenced snapshots are retained according to the personal-history and project-retention policies so the initiating player can request Undo or Redo without storing duplicate full documents inside Java collections.

The accepted operation and revision metadata exposed by the Project History and Recovery Panel is retained under the same finite server policy as the journal and snapshots. Metadata may remain inspectable after a referenced detail snapshot is cleaned up; the panel marks that detail `Unavailable` rather than reconstructing it or silently removing the history record. The panel is read-only and does not add a second unbounded audit log.
