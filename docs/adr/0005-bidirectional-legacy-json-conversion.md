# Preserve legacy camera-animation JSON through bidirectional conversion

For clarity, this decision uses Existing Runtime Camera Animation JSON to name the current per-channel resource format read by `CameraKeyframeAnimation.JSON_CODEC` and `StaticCameraAnimationReloadListener`; “legacy” means older than the new project document, not removed or automatically unsupported. Its JSON object carries animation fields and keyframe data, while the containing `ModifierType` resource path supplies the scalar channel context.

The rewritten editor must import and export the existing camera-animation JSON format in both directions. Import preserves every known legacy field and uses a retention strategy for unknown fields instead of silently discarding them. Because a legacy animation JSON document does not contain its `ModifierType`, a single-file import uses the currently selected scalar track or an explicit user-selected target; it never guesses the channel from keyframe values. A legacy directory import may use a verified `ModifierType` directory name, while an unknown directory requires explicit user selection or is rejected. The new project document may add editor extensions such as track identity, colors, curve controls, markers, viewport state, and explicit Project Format Version metadata. Project-format export includes confirmed marker names, times, and project metadata, but excludes local UI workspace state and uncommitted drafts. Importing a project file into a new project regenerates marker stable IDs to avoid identity collisions. Existing Runtime Camera Animation JSON export emits only fields that its reader understands and never writes project markers; importing it never creates markers. Compatibility export reports explicit warnings when newer concepts cannot be represented, while new-format export retains the extensions. Project Format Migration applies only between supported versions of the native project document; it never rewrites Existing Runtime Camera Animation JSON as a side effect.

Export is a Lock-Neutral Project Operation and serializes only the chosen server-accepted revision, never an uncommitted command draft. An import that replaces the current project document must complete a Destructive Project Preflight before its Destructive Project Lock Drain and mutation; an additive import remains an ordinary validated content transaction and cannot modify a currently locked command event unless the operation is submitted by its lock holder.
