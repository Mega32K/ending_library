# Keep collaborative-preview start and join explicit

When a player invokes Start Collaborative Preview for a Project that already owns an active Collaborative Preview, the server returns a bounded semantic `Already Active` result instead of admitting a second session. The result is non-blocking at the UI level: it explains that a shared preview is already running and exposes a separate Join Collaborative Preview action when the current player may be eligible to join.

The start-conflict result does not capture or replace the player's Local Preview Snapshot, change local playback, change the active Project Tab, acquire a participant slot, or enqueue a retry. It also never joins automatically, even when the player is the Project Owner or an authorized Project Editor. The separate Join action is itself the user's confirmation and submits directly without a second blocking dialog. It performs the normal server validation for permission, project lifecycle and format, active-tab identity, participant capacity, and preview-session generation; only an accepted join captures and applies the player's local preview restoration state.

The conflict notice and Join action are connection-local and generation-aware. After Join is submitted, it enters a single-flight non-blocking Joining state; repeated activation is ignored rather than queued. Before the server enters atomic application, the player may cancel, close the originating tab, or switch away, and the request is released without altering local preview state. If the active preview terminates, the project lifecycle changes, or the player loses eligibility, the server revalidates and rejects stale admission. Once atomic application begins, the request reaches one terminal result and delayed or duplicate responses are discarded by identity and request generation. Rejections are shown through the status bar and optional non-blocking notice, with Retry exposed only for authoritative transient causes. Repeated Start clicks do not create multiple notices or an unbounded queue; they coalesce into the current bounded status result.

This preserves the distinction between creating shared playback and explicitly entering it, while keeping the player's independent local inspection safe from accidental state replacement.
