# Imitate the vanilla command-entry experience

The camera editor's command field uses the familiar interaction model of Minecraft's command-block input and player chat command input. It is a focused single-line editor with ordinary cursor movement, selection, insertion, replacement, optional leading-slash convenience, server-backed completion, and immediate local presentation of syntax or validation feedback. The field should feel recognizable to players who already know those two vanilla command-entry surfaces, including predictable keyboard focus and text-editing behavior.

This is an input and presentation decision, not a runtime execution decision. Pressing keys while editing never dispatches a command, sends chat, changes the shared project, or bypasses the existing draft-validation boundary. Completion remains transient and authoritative-server-backed, accepted text remains a local draft until the properties action is confirmed, and only validated normalized text can become a shared Single-Command Event. The editor remains single-command-per-event rather than becoming a multiline command block.

The parity is intentionally limited to behavior that is useful and safe in an editor. The camera editor may show richer inline diagnostics and completion metadata than vanilla, but it must not imply that a draft has executed or that a chat message was sent. It does not maintain command history: while the completion menu is open, `Up` and `Down` navigate transient suggestions, and closing the properties editor clears an uncommitted draft rather than storing it for later recall. This keeps the familiar input feel while preserving collaboration, permission, serialization, and Undo/Redo semantics already defined for command events.
