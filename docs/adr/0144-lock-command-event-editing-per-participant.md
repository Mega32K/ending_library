# Lock command-event editing per participant

The initial camera editor uses a temporary personal edit lock for one Command Animation Effect Event. When an authorized participant enters that event's command-editing surface, the server grants the lock to that participant and advertises the lock state to the active Editing Session. While the lock is held, other participants may view the last accepted event, select it, preview the animation, open the runtime diagnostic panel, and edit unrelated project content, but they cannot mutate any part of the locked event's authored state.

This is a deliberately narrow exception to the general optimistic, non-locking collaboration model. It prevents two command authors from typing over one another and avoids ambiguous local drafts for executable content, while preserving parallel work on other events and tracks. It is not a project lock, track lock, permission change, or transfer of ownership. A participant who attempts to edit a locked event receives a non-blocking explanation identifying that another participant is currently editing it; the editor does not silently queue or overwrite the attempted draft.

The lock is associated with the event's stable identity and the active Editing Session, not with a screen selection or a diagnostic record. Its protected footprint is defined by ADR-0145 and its acquisition, release, and stale-lock recovery lifecycle is defined by ADR-0146. Only the lock holder's validated confirmation can create the next shared event revision, and no lock may remain retained after the holder's connected lifecycle ends.
