# Make checkpoint restoration undoable without deleting personal history

Checkpoint restoration remains an owner-only, explicitly confirmed operation exposed by the Checkpoint Management Panel. It first displays a bounded Checkpoint Difference Summary and automatically protects the current authoritative state. If active Command Event Lock Leases would be affected, the initial attempt is blocked until the owner either cancels or explicitly authorizes a Checkpoint Restore Preflight and the possible later draft loss at its commit boundary. Failed preflight preserves the original locks and drafts; only successful preparation may proceed to the Destructive Project Lock Drain. The selected Named Project Checkpoint label is not written over the project as a historical rewind. Instead, the server applies the label's target Revision Commit Node content as one new authoritative full-document revision whose parent is the current mainline head, after creating a Protection Checkpoint for the pre-restore state. All later project history remains available and the mainline never moves backward.

The summary starts with project-level counts for changed animations, scalar tracks, authored keyframes, curve segments, command events, markers, and animation properties. It then offers expandable animation- and track-grouped Checkpoint Difference Detail with concise before-and-after values, including keyframe times, values, interpolation or curve changes, command text changes, marker names and times, and property changes. Large detail sets use a bounded scrollable virtual list rather than rendering an unbounded document dump. A Checkpoint Target Preview action opens the selected checkpoint in the existing local read-only preview path without changing the active project, current collaboration state, playhead, drafts, or runtime instance. An optional raw-data view is read-only and secondary; it never becomes the default presentation.

The restore operation is appended to the initiating player's Personal Edit History as one special Restore Checkpoint entry. Existing Undo and Redo records are not cleared or silently discarded. The entry stores stable references to the target checkpoint and the pre-restore Protection Checkpoint, plus the revisions and document fingerprints needed for conflict validation; it does not retain a second full project document in an in-memory shortcut stack.

Undoing a restore is itself a new server-ordered compensating operation that restores the Protection Checkpoint. Redoing it is another compensating operation that restores the original target checkpoint. Both operations use a full-document Restore Footprint. Therefore, if any accepted content edit from any participant occurs after the restore or after its undo, the corresponding compensation is rejected as an Undo Conflict unless the server can prove that no conflicting project state changed. No restore undo or redo may silently overwrite another participant's edits.

The project receives a Restore Barrier at the restore revision. Personal history entries from before the barrier remain stored and inspectable, but their eligibility is revalidated against the barrier and later revisions. An entry may be temporarily suspended because the restored state removed or replaced its target; it becomes eligible again only when the restore chain is safely compensated and its own footprint can be applied. Entries created after the restore follow ordinary field-level conflict rules. If a new normal edit creates a branch that invalidates a Redo action, the Redo entry becomes unavailable rather than being silently applied; retention and lifecycle cleanup may remove it later under the bounded history policy.

Every connected editor receives the restored authoritative document through one Restore Content Refresh. All open editable views of that project replace stale authored content atomically without closing their tabs or removing them from the Editing Session. Restore Draft Invalidation cancels local Animation Properties, Auto Key, Command Event Creation, and active Gesture Preview drafts because their baselines are no longer valid; a draft is never silently merged into the restored document. Restore Selection Reconciliation preserves valid local selections and removes only selections whose identities disappeared, while preserving each player's playhead, playback state, viewport, panel layout, and other valid observation state. No participant is forced to seek to the restore target's playhead, join Collaborative Preview, or change an active gameplay/runtime camera. The initiating restore dialog closes with its result, while other participants receive a non-modal Collaboration Status Area notification identifying the restore origin. Other participants' personal histories are not cleared, but their pre-barrier operations are marked for revalidation so an old Undo cannot resurrect content that the owner intentionally restored away. The restore itself is visible as a project revision to every collaborator even though only the initiating player's shortcut history contains the direct restore entry.

The design trades convenience for safety: restoring a large checkpoint can make Undo/Redo conflicts common and requires retaining checkpoint references longer, but it avoids silent data loss, preserves auditability, and prevents unbounded duplicate memory copies. Snapshot references must be lazy and retention-bounded; a checkpoint cannot be compacted while an eligible history entry still references it. Once the restore entry expires or becomes permanently unavailable, its protection reference may be released through the normal retention lifecycle.
