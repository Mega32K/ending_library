# Keep referenced checkpoints and clean only unreferenced history

Project version retention is designed for substantial editing sessions without becoming an unbounded memory or disk sink. The server keeps a generous, configurable number of recent Project Snapshots, lightweight Revision Commit Node metadata, and Named Project Checkpoint metadata, but applies a finite storage budget and a bounded personal Undo/Redo history. Exact defaults are load-test and deployment decisions rather than hidden behavior in the client.

A checkpoint may be marked pinned by the owner. In addition, the retention manager tracks references from eligible Restore Checkpoint Operations, Protection Checkpoints, active Collaborative Preview Revision Snapshots, recovery records, and any other explicitly durable feature. A pinned or referenced checkpoint is protected from automatic deletion. References are stored as stable IDs or snapshot paths and revision metadata; loading a full document is lazy and occurs only when the operation actually needs it.

Multiple checkpoints targeting the same revision share one reconstruction anchor. Pinning any one of them protects that anchor, while deleting one releases only that checkpoint's reference. The anchor becomes cleanup-eligible only after every checkpoint, history action, preview, and recovery reference has been released. A finite pin budget rejects a new pin when exhausted and never unpins or evicts another checkpoint automatically.

When the retention budget is exceeded, cleanup first compacts journal entries covered by a valid Project Snapshot, then selects the oldest checkpoint that is neither pinned nor referenced. Cleanup never deletes the newest valid recovery base, the active project snapshot, or the only snapshot needed to replay a surviving journal. If a version is eligible but currently in use, it enters Pending Cleanup and is removed only after all references are released. Cleanup is deterministic and does not evict a random active version to satisfy a new request.

An Undo/Redo record stores operation metadata, revision and document fingerprints, stable object references, and checkpoint references rather than a complete project copy. If a referenced checkpoint is eventually unavailable because its history entry expired or the owner explicitly deleted it after it became unreferenced, the corresponding history action remains visible but is marked Unavailable and cannot be executed. The server never reconstructs it from an approximate or unrelated snapshot.

The Checkpoint Management Panel exposes checkpoint reference and retention state to both Owners and Editors for inspection. Only the Owner may pin or unpin a checkpoint, restore it, or request deletion; Editors may create checkpoints and inspect their metadata but receive disabled-button explanations for owner-only mutations. Manual deletion of a pinned checkpoint requires explicit owner confirmation and shows the references that will become unavailable after deletion. Manual deletion never removes an active or still-referenced checkpoint immediately; it marks the checkpoint reference for deletion and reports which history or preview references must expire first. Deleting or expiring a checkpoint never rewrites the Revision Commit Node mainline or removes another checkpoint pointing to the same node. Retention cleanup, checkpoint deletion, and reference release are server-side lifecycle operations and must not leave stale in-memory document copies.
