# Ship first-class Bézier curve authoring in the initial release

The initial rewritten Camera Animation Editor includes editable cubic Bézier control points as a complete authoring and runtime feature. Control handles are not decorative graph overlays and custom curves are not deferred to a later release. A curve edit must survive closing and reopening the project, real-time collaboration, revision changes, checkpoint restoration, clipboard operations, Undo/Redo, persistence, runtime publication, and camera playback.

Each interval remains an independent Curve Segment with stable start and end keyframe identities, normalized forward-time control coordinates when applicable, overshoot-capable value coordinates, and a boundary-level Tangent Mode. Bézier participation is organized into adjacent Timeline Bézier Node Chains: exactly two adjacent nodes intentionally render and evaluate linearly, while three or more render the authored continuous Bézier result. A coupled boundary may deliberately include adjacent segments in one edit transaction. The graph renders the exact active result evaluated by the runtime. A handle drag previews continuously on the editing client, then submits one atomic server-validated edit transaction on release; cancellation restores the pre-gesture segment without creating a revision or Undo/Redo entry.

All native serialization and transport surfaces used by the new project and runtime pipeline preserve the curve data losslessly and version it explicitly. Extended Camera Animation JSON also carries optional versioned custom-curve fields and retains `easing` as an explicit compatibility fallback; files without curve fields preserve the original easing-only meaning. Legacy-compatible exports remain available through the separate downgrade-warning flow, and legacy input migrates deterministically through Legacy Curve Mapping.
