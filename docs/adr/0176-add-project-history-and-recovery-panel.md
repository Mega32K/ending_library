# Add a read-only project history and recovery panel

The File menu opens a responsive, dockable Project History and Recovery Panel for the active project. Both Project Owners and Project Editors may inspect the panel. It lists the finite server-retained sequence of accepted project revisions and atomic operations plus bounded Runtime Publication Records, with the operator, event time, operation type, affected scope, authoritative revision where applicable, and persistence or outcome state. The panel supports filters for operator, operation type, time range, checkpoint, restore events, and runtime publication events.

The main history presentation uses a compact Git-inspired single-mainline revision graph. Every accepted atomic edit appears as a Revision Commit Node, the current accepted head is explicit, and Named Project Checkpoints appear as compact badges on their immutable target nodes. Multiple checkpoints may share one node. The graph has no branch lanes, detached head, merge, cherry-pick, staging, or working-tree controls.

Each record can expose a read-only difference summary and expandable detail when the required operation and checkpoint references remain available. The panel never includes local content drafts, Animation Properties previews, Auto Key proposals, command input history, or other transient authoring state. If metadata survives but a referenced checkpoint, snapshot, or detailed diff has been cleaned up, the record remains inspectable and explicitly shows `Unavailable`; the client must not reconstruct or approximate the missing content.

The panel is an inspection and recovery surface, not another editing history. Opening it does not create a revision and does not change the active project tab, playhead, playback state, selection, workspace layout, editor preview, or runtime camera. It does not execute personal Undo or Redo directly. A restore action continues through the existing permission check, Checkpoint Restore Preflight, difference summary, and atomic checkpoint-restore flow; the panel cannot bypass those safeguards.

The server applies a finite retention policy to history metadata and detail references. Expired detail is released without deleting still-retained metadata, and the UI reports the resulting availability state rather than silently dropping the record. History inspection is available only for the current server-retained project history and does not become a permanent chat log or a player-local archive.

History rows are loaded through server-side cursor pagination. Opening the panel requests one bounded page; approaching the end requests the next page under the same filter and project baseline. Changing a filter discards the visible result and starts a new cursor sequence. Difference summaries and detailed differences are separate on-demand requests, and the client keeps only a finite page/detail cache that is released when the panel closes or the project session changes.

Owner and Editor may invoke Create Checkpoint Here on an available historical Revision Commit Node. The server must first verify that the node can be reconstructed durably; failure leaves no partial checkpoint. System Recovery Points are visible only through an explicit filter and carry a non-editable system indicator. They are not ordinary user checkpoints and remain governed by their migration, restore-protection, or recovery lifecycle.
