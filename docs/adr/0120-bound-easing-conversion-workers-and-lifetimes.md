# Bound Easing conversion workers and lifetimes

Authoritative Easing-to-Bézier recomputation runs through a camera-editor-owned bounded executor rather than the shared common pool or the Minecraft server tick thread. The executor has finite concurrency and queue capacity, and a player may have at most one active conversion confirmation task for a project. A task captures only immutable source data, project identity, baseline revision, requester UUID, algorithm version, fidelity settings, and bounded budget values; it never captures a `Player`, `Level`, editor screen, project document, or other world-owned mutable object. Cancellation is cooperative and the result is discarded if interruption arrives, while completion is finalized on the server thread where permission, session, revision, footprint, and lifecycle state are checked again. Disconnect, project close, authorization loss, server shutdown, timeout, rejection, and exception release the task handle and captured snapshot through the same terminal cleanup path.
