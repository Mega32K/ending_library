# Complete checkpoint target, comparison, and lifecycle rules

Multiple Named Project Checkpoints may point to the same Revision Commit Node. Each checkpoint keeps an independent stable identity, name, description, creator, creation time, pin state, and lifecycle state, while all checkpoints on the same revision share one durable reconstruction anchor. No duplicate Project Document or snapshot is stored merely because another checkpoint points to that revision. Deleting, unpinning, or renaming one checkpoint never changes another checkpoint or its common target.

Checkpoint names are non-empty after trimming and are unique within one project under case-insensitive comparison. The server validates the name and finite text budgets for both creation and metadata editing. A conflicting name is rejected with the current checkpoint list state and a suggested available name; the server never silently renames an accepted checkpoint. Every rename dialog selects the existing text on open under the shared rename-input contract.

File > Create Checkpoint targets the current server-accepted mainline head after the established accepted-content flush. The Project History and Recovery Panel additionally offers Create Checkpoint Here for any retained, reconstructable Revision Commit Node. Historical creation neither restores that revision nor creates a branch. Before exposing the checkpoint, the server validates the node and guarantees a durable reconstruction anchor by retaining the required snapshot-and-journal chain or atomically materializing a snapshot. If that cannot be guaranteed, creation fails without a partial checkpoint.

The Checkpoint Management Panel groups multiple checkpoints under their common revision while preserving direct search and list views. The Project History and Recovery Panel presents the single mainline as a Git-inspired vertical revision graph with a current-head indicator and compact checkpoint badges on their target nodes. It does not imitate a complete Git client: there are no branch lanes, detached heads, merge commits, cherry-pick controls, staging area, or working-tree terminology.

Checkpoint comparison defaults to the selected checkpoint versus the current accepted mainline head. Users may instead select another available checkpoint or Revision Commit Node as the read-only comparison target. Difference computation remains server-derived, bounded, virtualized, and on demand; local drafts and command input history are never included. Target preview and comparison do not create revisions, acquire content locks, or change playback, preview, publication, or runtime camera state.

Periodic persistence snapshots remain implementation details and are not displayed as user checkpoints. Migration Protection Checkpoints, pre-restore Protection Checkpoints, and other server-created recovery references appear only as System Recovery Points in the Project History and Recovery Panel under an explicit filter. They use a distinct system indicator, may be inspected when compatible, and cannot be renamed or manually deleted while referenced. Their corresponding recovery or compensation workflow remains authoritative.

Pinning protects the checkpoint and the shared reconstruction anchor needed by every live reference to its target. The pin and storage budgets are generous but finite; exceeding either rejects the new pin or checkpoint with a specific reason and never evicts another pinned checkpoint automatically. Once no checkpoint, undo/redo entry, preview, recovery record, or other protected feature references a target, normal deterministic retention cleanup may release its materialized content while retaining whatever lightweight revision metadata remains permitted.

Ordinary project export contains the selected accepted project content, not the operation graph, personal histories, or the project's checkpoint collection. Exporting from a checkpoint preview exports only that checkpoint's reconstructable project content through the existing project or runtime export validation path; importing it creates or updates content through the normal import workflow and does not recreate the source project's checkpoint history.
